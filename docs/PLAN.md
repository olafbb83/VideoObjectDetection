# VideoDetection — план проекту

**Мета:** детекція людей і аналіз їх поведінки на відео з ESP32-S3 CAM.
**Головна ціль — навчальна:** освоїти ESP32CAM, стрімінг, OpenCV, YOLO, повний ML-цикл.

Англомовний опис проекту й інструкції запуску — [README.md](../README.md).
Усі заміри — [benchmarks.md](benchmarks.md).

## Архітектура

```
ESP32-S3 CAM ──MJPEG/WiFi──> ХАБ ──> YOLO detect або pose ──> трекінг ──> правила
   "око"                   (ноут/RPi5)                                       │
                                                                    веб-UI + події
                                                              (браузер, смартфон, API)
```

YOLO **не** крутиться на ESP32 — у неї ~8 МБ PSRAM і векторні інструкції, чого
вистачає лише на крихітні ESP-DL моделі. ESP32 = камера + Wi-Fi транспорт.

**Хаб — єдиний споживач камери:** один читач, один прохід моделі, глядачі
забирають готовий кадр. Перевірено: 3 глядачі не просідають (19.7/19.9/19.8 fps),
тоді як прямі підключення до ESP32 діляться каналом (13.3 + 7.4 на двох).

**Залізо:** ноут (Core Ultra 7 155H, iGPU Arc + NPU) для розробки й навчання,
RPi 5 8GB для фінального цілодобового деплою.

### Етап 0 — Каркас ✅

Структура репо, git, PlatformIO-проект, venv, requirements.

### Етап 1 — Камера стрімить ✅

Прошивка `firmware/esp32s3_cam`: MJPEG на `:81/stream`, `/status` з телеметрією
(включно з причиною ребуту й кількістю глядачів), `/control` для зміни режимів
на льоту, mDNS, авто-reconnect. Деталі — `firmware/esp32s3_cam/README.md`.

**Результат:** VGA 29-34 fps, SVGA 29, HD 16-18. VGA і SVGA впираються в стелю
самого сенсора OV2640. Робочий режим — **VGA**.

### Етап 2 — Приймач на Python ✅

`hub/camera.py`: MJPEG розбирається вручну, читач в окремому потоці тримає
**лише останній кадр**. `cv2.VideoCapture` не підійшов саме тому, що черга
кадрів накопичує затримку без обмежень.

**Дві знахідки, які вилізли тільки через заміри:**
- `cv2.waitKey(1)` на Windows коштує ~15 мс, а не 1 мс (гранулярність
  системного таймера). Показ просідав з 22 до 10 fps. Заміна на `cv2.pollKey()`.
- Буфер читання 64 КБ при кадрі 14 КБ давав пачки по ~4.6 кадру з паузами
  200 мс. Поки споживач був миттєвий — нешкідливо; з YOLO решта пачки
  перезаписувалась, і 23 fps прийому давали 10 fps обробки. Буфер 8 КБ.

### Етап 3 — Перша детекція ✅

YOLO11n на COCO, фільтр по класу `person`. Розібрали `conf`, `iou`, `imgsz`,
NMS. Бенчмарк бекендів — прискорювачі дають 3-4×: iGPU @640 = 14.3 мс проти
57.5 мс у PyTorch на CPU. NPU виграє на 320 і найстабільніший по p95.

### Етап 4 — Хаб ✅

`hub/pipeline.py` + `hub/server.py`: FastAPI на HTTPS:8443, токен скрізь крім
`/health`, `compare_digest` проти timing-атак, самопідписаний сертифікат
з правильним SAN (браузери ігнорують CN), EC P-256 замість RSA.

### Етап 5 — Трекінг і поведінка 🔄

**ByteTrack ✅.** Конфігурацію підбирали на **записаному ролику**, бо наживо
прогони непорівнювані. Стокова: 18 ID, медіана треку 0.7 с. Підібрана
(`hub/trackers/bytetrack_tuned.yaml`): **6 ID, медіана 3.9 с**. Найдієвіший
параметр — `match_thresh`; `track_buffer` не дав нічого.

**Зони й лінії ✅.** `hub/zones.py`: точка прив'язки — ноги, а не центр рамки;
перетин ліній як перетин **відрізків**; два дебаунси — 3 кадри на межі зони
і 1.5 с перед забуттям треку. Координати нормовані 0..1.
Редактор мишею — `hub/zone_editor.py`. Тести — `tests/test_zones.py`.

**Pose ✅.** `--pose` підмінює детектор (yolo11n-pose сама детектує людей).
+4% на iGPU, але **+32% на CPU** — важливо для RPi5.

**Падіння ⬜.** Основа готова: `hub/pose.py` рахує нахил тулуба, пропорції
рамки й висоту тазу. Головна складність не в геометрії: падіння — це **подія
в часі**, а не поза. Людина, що лягла на диван, і людина, що впала, у статиці
однакові; різниця у швидкості переходу. Потрібна машина станів на трек,
а не поріг кута.

**Ще не зроблено:** події → MQTT / Telegram, збереження кліпів.

### Етап 6 — Датасет і навчання 🔄

Два рівні, і це **два різні тренування**:

*Рівень 1 — детектор під свою камеру.* 500-2000 кадрів з власної ESP32
(шум OV2640, ракурс, контрове світло, дрібні фігури). Розмітка в CVAT/Label
Studio, auto-labeling великою YOLO11x з ручною правкою. Fine-tune YOLO11n,
читання метрик: precision/recall, mAP50, mAP50-95, confusion matrix.
Порівняння baseline vs fine-tuned на власному test-сеті.

**Чому це наступний крок, а не опція:** ми двічі вперлись у якість детектора.
Треки рвуться там, де модель невпевнена (10-й перцентиль впевненості 0.56),
і зони промахуються, коли ноги обрізані краєм кадру. Налаштування трекера
вичерпані — 6 ID при теоретичному мінімумі 5-6.

*Рівень 2 — класифікатор дій.* Поведінку не розмічають боксами. Датасет —
**послідовності**: вікна по N кадрів з pose-координатами. Модель — LSTM/GRU
або градієнтний бустинг по фічах скелета, поверх YOLO-pose. Класи на кшталт
стоїть / йде / біжить / сидить / впав. Це ж дає й детекцію падіння.

### Етап 7 — Деплой на RPi 5 ⬜

Експорт у NCNN/ONNX (`hub/export.py --format ncnn`), INT8-квантизація,
бенчмарк, systemd-сервіс, автозапуск.

**Бюджет уже відомий:** на CPU pose коштує +32% проти detect. Реалістично
YOLO11n-pose @320 NCNN INT8 ≈ 10-15 FPS — для поведінкової аналітики
достатньо. Опційно Hailo-8L AI Kit (~$70) для ~30+ FPS.

### Етап 8 — Опції ⬜

ESP-DL детекція руху на самій ESP32 як wake-on-motion (щоб не стрімити 24/7),
VLM через локальну Ollama для текстових описів подій, кілька камер.

## Орієнтири по часу

- ✅ працюючий детектор з веб-переглядом — зайняв приблизно тиждень
- повний цикл з власною моделлю на RPi5 — ~4-6 тижнів від старту

## Граблі заліза

- **живлення:** стабільні 5V / ≥1A, інакше випадкові ребути під навантаженням.
  Причину видно в `/status` → `reset_reason` = `BROWNOUT`
- **перегрів** модуля при тривалому HD-стрімі 24/7
- **Wi-Fi тільки 2.4 ГГц**, MJPEG їсть 1.7-3.4 Мбіт/с на камеру
  (розмір кадру плаває в півтора раза залежно від сцени)
- **глядачі діляться каналом:** відкрита вкладка браузера вдвічі ріже FPS
  у Python-клієнта. Кількість видно в `/status` → `clients`
