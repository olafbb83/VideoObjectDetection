## Головне про цей проект

**Це навчальний проект.** Основна ціль власника — самому вивчити ML/OpenCV/YOLO,
сфера для нього нова. Тому: пояснювати концепції перед кодом, називати терміни
правильно й розшифровувати при першій появі, не пропускати етапи заради швидкого
результату. Спілкування українською.

Власник має солідний досвід з ESP32 та сенсорами — ембедед-базу пояснювати не треба.

## Важливі обмеження

- **Глядачі потоку ділять спільну пропускну здатність.** Камера обслуговує
  кількох клієнтів, але сумарний FPS не росте: два клієнти дали 13.3 + 7.4 там,
  де один отримував 21. Відкрита вкладка браузера з `http://esp32cam.local/`
  вдвічі ріже FPS у Python-клієнта — під час замірів її треба закривати.
  `/status` на порту 80 живий завжди, поле `clients` показує кількість глядачів.
- Камера доступна як `esp32cam.local` (mDNS). Після переїзду мережа інша:
  IP зараз `192.168.0.184` (DHCP, може змінитись).
- **Модуль камери замінено: зараз стоїть OV5640** (PID 0x5640), а не OV2640.
  Прошивка обирає налаштування за PID сенсора (профілі в `main.cpp`), поверх
  них можуть лягти збережені у флеш через `/save` — окремо для кожного сенсора.
  Заміри етапу 1 (30 fps стеля, 9-14 КБ кадр) стосуються OV2640 і для OV5640
  НЕ дійсні.
- **OV5640: FPS визначає XCLK, а не мережа** (~1 кадр на МГц; якість JPEG
  міняє розмір кадру, але не FPS). **Смуги — взаємодія освітлення і XCLK:**
  зі світлом їх немає навіть на 20 МГц, у темряві на 20 МГц кадр майже
  знищений, на 8 МГц чисто. Механізм не встановлено: гіпотеза про підсилення
  шуму не пояснює величину ефекту. Таблиці — `docs/benchmarks.md`.
  Підбір для нового модуля — `hub/camera_tune.py` (сцена нерухома, вкладки
  з камерою закриті, заміряти і зі світлом, і в темряві).
- Орієнтація OV5640 на цій платі перевірена користувачем: дзеркало 1, переворот 0.
- **Авто-XCLK для OV5640: 16 МГц світло / 8 МГц темрява, рішення за ПІДСИЛЕННЯМ
  сенсора** (регістри 0x350A/0x350B), пороги 60/160, увімкнено в профілі.
  Не за яскравістю кадру (AEC тримає її сталою) і не за експозиція×підсилення:
  обидва варіанти добутку (сирий і поділений на XCLK) спростовані калібруванням.
  Сутінки не міряли — якщо `auto_switches` у `/status` швидко росте, пороги
  треба розводити.
- Датасет для етапу 6 ще не збирався — збирати вже з OV5640: інший сенсор
  дає інший шум, кольори й динамічний діапазон, тобто інший домен.

```bash

C:\Users\Lenovo\.platformio\penv\Scripts\pio.exe run -d firmware/esp32s3_cam -t upload

.venv\Scripts\python.exe hub\detect.py --model 640 --device intel:gpu --track --pose --zones

# експорт моделей (перед першим запуском з --device intel:*)
.venv\Scripts\python.exe hub\export.py

# тести геометрії (не потребують камери)
.venv\Scripts\python.exe tests\test_zones.py

# прогін по запису замість камери — для порівнюваних замірів
.venv\Scripts\python.exe hub\detect.py --source docs\track_test.mp4 --model 640 --device intel:gpu
```

## Хаб (етап 4)

- `hub/pipeline.py` — ЄДИНИЙ споживач камери: один читач + один прохід YOLO,
  глядачі забирають готовий кадр. Не давати кожному HTTP-клієнту свій
  MjpegCamera: перевірено, 3 глядачі не просідають (19.7/19.9/19.8 fps).
- `hub/server.py` — FastAPI на HTTPS, порт 8443. Токен обов'язковий скрізь,
  крім `/health`. Приймається як `Authorization: Bearer` або `?token=`
  (тег `<img>` не вміє слати заголовки, а MJPEG живе саме в `<img>`).
- `secrets/` — токен, сертифікат, ключ. У git не потрапляє.
- Сертифікат самопідписаний (`hub/make_cert.py`). Браузери дивляться **тільки
  в SAN**, тому адресу треба вписати туди: `--extra <ім'я або IP> --force`.
  Коли з'явиться домен — просто підмінити файли на Let's Encrypt, код той самий.

## Трекінг і правила (етап 5)

- `hub/trackers/bytetrack_tuned.yaml` — типовий трекер, підібраний замірами
  (6 ID замість 18 на `docs/track_test.mp4`). `match_thresh` 0.9 — найдієвіший
  параметр; `track_buffer` не дає нічого.
- `--conf` для трекінгу 0.45, для чистої детекції 0.35. Нижчий поріг **гірший**:
  слабкі детекції на цій камері — сміття, трек на нього зповзає.
- `hub/zones.py` — зони й лінії. Точка прив'язки типово **нижня середина рамки**
  (ноги), не центр. Дебаунс 3 кадри проти тремтіння на межі; витримка 1.5 с
  перед забуттям треку, бо 62% провалів детекції тривають 1-3 кадри.
- Координати в `docs/zones.json` **нормовані 0..1** — переживають зміну
  роздільності камери.
- `hub/zone_editor.py` — малювання зон мишею по кадру з камери.
- `tests/test_zones.py` — геометрія без камери й моделі. Запускати після
  будь-яких змін у `zones.py`: помилка в знаку не падає, вона тихо плутає
  «увійшов» і «вийшов».
- `hub/pose.py` + прапорець `--pose`. Pose **підмінює** детектор, а не додає
  другу модель: yolo11n-pose сама детектує людей. Наслідок — лише клас `person`.
  Ціна: +4% на iGPU, але **+32% на CPU**, тобто на RPi5 це відчутно.
- `hub/export.py` — експорт моделей під конкретний imgsz (openvino / ncnn / onnx).
  Розмір входу зашивається в граф, тому для 320 і 640 потрібні різні теки.
- `--device intel:*` працює лише з експортованою моделлю; при `.pt` скрипт
  тепер дає зрозумілу підказку замість стектрейсу з torch.
